# 04 — Memory OS Architecture (`forge-memory`)

> **Status**: APPROVED ARCHITECTURE DRAFT | **Target**: Forge OS v0.2+  
> **Package**: `forge-memory` (Hierarchical Memory Engine)

---

## 1. Purpose

Memory OS manages the persistent, multi-tiered memory hierarchy of Forge OS. It ensures that agents maintain precise context during active tasks, retain historical project knowledge across sessions, eliminate memory bloat via automated garbage collection, and avoid repeating past failures.

---

## 2. Responsibilities

1. **Hierarchical 5-Layer Storage**: Provide structured, latency-tiered memory from ephemeral turn context down to cross-project experience archives.
2. **Decision Graph Maintenance**: Map why specific architectural choices were made and link them to user requirements.
3. **Post-Mortem & Pattern Stores**: Persist canonical records of fixed bugs and proven implementation patterns.
4. **Context Zone Management**: Enforce the 0–40% "Smart Zone" rule, preventing models from degrading into the "Dump Zone".
5. **Memory Garbage Collection**: Prune stale scratch files, expired session tokens, and redundant trace logs.

---

## 3. The 5-Layer Memory Hierarchy

```
┌────────────────────────────────────────────────────────────────────────┐
│ L0: SESSION MEMORY (Ephemeral Context Scratchpad)                      │
│ • In-memory per-turn scratchpad                                        │
│ • Cleaned between builder-critic cycles to ensure clean-slate review   │
├────────────────────────────────────────────────────────────────────────┤
│ L1: PROJECT MEMORY (Local Workspace Ledger)                            │
│ • .forge/state.json, .forge/goal_contract.json, .forge/ledger.jsonl    │
│ • Working branch diffs and local test execution breadcrumbs            │
├────────────────────────────────────────────────────────────────────────┤
│ L2: SKILL MEMORY (Executable Operating Rules)                         │
│ • gauntlet-operator SKILL.md, procedural checklists, test harnesses    │
│ • Domain-specific task recipes and validation scripts                  │
├────────────────────────────────────────────────────────────────────────┤
│ L3: KNOWLEDGE MEMORY (Canonical System Truth)                          │
│ • Git repository commit tree, architectural ADRs, schemas, APIs        │
│ • Project-level dependency manifests and documentation                 │
├────────────────────────────────────────────────────────────────────────┤
│ L4: EXPERIENCE MEMORY (Long-Term Vault Archive)                        │
│ • Google Drive synced post-mortems, failure ledgers, pattern libraries │
│ • Historical performance benchmarks across model generations           │
└────────────────────────────────────────────────────────────────────────┘
```

---

## 4. Specialized Memory Subsystems

### 1. Decision Graph (`.forge/decisions/`)
- Tracks architectural forks, alternatives considered, and the justification for selection.
- Schema: `decision_id`, `state_phase`, `selected_option`, `rejected_options`, `justification`, `scope_hash`.

### 2. Post-Mortem Store (`.forge/memory/post_mortems/`)
- Persistent records generated by the Debug Circuit when non-trivial bugs are cracked.
- Schema: `incident_id`, `symptom`, `root_cause_mechanism`, `fix_commit`, `why_it_slipped_through`.

### 3. Pattern Library (`.forge/patterns/`)
- Golden architectural templates and verification harnesses proven to pass the Execution Gauntlet.

### 4. Memory Garbage Collection (GC)
- **Trigger**: Run on every state transition from `EXECUTING` to `VERIFYING` or when `.forge/` exceeds 500MB.
- **Rule**: Retain all structured decision records, commit pointers, and Goal Contracts; archive raw stdout/stderr blobs older than 7 days to Google Drive; purge local ephemeral scratchpads.

---

## 5. Inputs & Outputs
- **Inputs**: Tool execution logs, Git diffs, Goal Contract updates, Critic reports, user feedback.
- **Outputs**: Synthesized context prompts for workers, clean-slate evaluation packets for critics, long-term post-mortem indices.

---

## 6. Failure Modes & Defenses
- *Failure Mode 1: Context window saturation (Context Rot)*.  
  **Defense**: Hard context ceiling at 40% of provider limit; automatic compaction and offloading to L1/L4.
- *Failure Mode 2: Hallucinated memory recall*.  
  **Defense**: Every recalled fact must carry an empirical citation (`file:line` or Git commit hash).
